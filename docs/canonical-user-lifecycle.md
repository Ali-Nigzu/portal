# Canonical lifecycle against the locked live contract

Correction base: `e3de572c9c9b89ba00d3a152e080d19b20bfc25b`.
Production schema and grants were already applied manually by the owner. This
correction only changes application/source/test files; it does not connect to
production PostgreSQL, run live migrations/grants, send live email or change GCP.

## Durable identity and credentials

`CanonicalUser` and all canonical user SELECTs contain exactly seven fields:
`id`, `email`, `username`, `phone_number`, `password_hash`, `status`,
`session_version`. The database additionally owns `created_at`. Login uses only
`public.users`, case-insensitive username/email lookup, status 1 and Argon2.
It does not read or write lifecycle storage, and has no JSON fallback.

Signup inserts email, username, phone_number, password_hash, status 1 and
`created_at = CURRENT_TIMESTAMP`. The existing created_at column is NOT NULL
with no default. The INSERT omits id; `public.users_id_seq` and the existing
`GENERATED BY DEFAULT AS IDENTITY` generate it. Existing IDs including 0/1 are
preserved. No organisation or membership is created. The entered username is
the canonical username; `name` remains its existing API wire field.

Shared `services/passwords.py` generates/verifies Argon2 credentials for signup,
reset, password change and login. Passwords are not trimmed; the existing eight
character minimum and 1,024 character request bound remain. Identity/credential
changes never write JSON. Normal profile updates affect only submitted fields;
omitted phone is untouched, removal writes NULL, and email remains read-only.
Concurrent edits to the same field use the last successful transaction. There
is no optimistic account-version contract.

Signed browser sessions retain canonical user ID, session_version and their
existing issuance/expiry/nonce fields. Protected requests reload the enabled
canonical user and compare versions. Reset/password change increment the version
atomically with the hash change and delete that user's pending/verified reset and
unlock challenges. Other old sessions fail. Account password change replaces the
current browser cookie after commit; forgotten-password reset returns to Login.
The existing fixed 365-day session lifetime and signed session format remain.

## One temporary challenge table

Only `public.user_lifecycle_challenges` stores temporary lifecycle state. Its
exact columns are id, purpose, user_id, payload, code_hash, code_expires_at,
attempts, resends, last_sent_at, verified_at, consumed_at, created_at.
Purpose is smallint: 0 signup, 1 reset, 2 unlock. Attempt/resend counters are
smallint; timestamps/payload/defaults match migration 002 and the locked contract.

Each journey gets a cryptographically random opaque 32-byte handle. Only its
SHA-256 digest is stored as id; incoming handles are digested for lookup.
Codes are stored as HMAC digests keyed with the existing stable session secret,
never plaintext. Signup payload contains exactly email, username, optional phone
and an Argon2 password_hash. Reset/unlock payloads are empty; the canonical user
is referenced through user_id and reloaded for eligibility and email delivery.
No signed lifecycle grant/helper or additional credential store is introduced.

Pending journeys last at most one hour from created_at. Codes last 15 minutes,
with five total wrong attempts, five resends and a 30-second cooldown. Resend
replaces the code hash/deadline, updates last_sent_at and preserves attempts.
Wrong-attempt counters commit before the HTTP error is raised. Verified or
consumed rows cannot verify or resend their code again.

Signup locks its challenge, verifies the code and rechecks identifiers; user
INSERT and challenge DELETE commit together. Verification/consumption timestamps
are set inside that transaction before deletion. Existing unique indexes
`uq_users_email_ci` and `uq_users_username_ci` enforce case-insensitive uniqueness;
ordered advisory identifier locks also prevent cross-column login ambiguity.
Unique violations map to deliberate 409 responses. Parallel completion creates
one user and the completed signup row is removed immediately.

Reset verification sets verified_at, retaining the same handle/row for the new
password step. That step requires an enabled canonical user, verified_at,
consumed_at NULL and a ten-minute window derived from verified_at. It updates
password_hash/session_version and removes the reset row atomically. Replay fails
because the row no longer exists. Independent reset completions serialize on the
user lock; the winning credential change removes the other working rows.

My Account unlock requires a canonical session, current Argon2 password and
Postmark code. Verification sets verified_at; the row authorizes edits for five
minutes and remains available for multiple profile changes. Each mutation checks
purpose 2, current authenticated user ID, row user_id, verified_at, consumed_at
NULL and the derived deadline. `unlockToken` is the existing wire name for the
same opaque challenge handle, not a second grant. The browser keeps it in page
state and a matching HttpOnly cookie. A different user cannot use that row. The
existing Lock editing action calls `/api/settings/unlock/end`, deleting the row;
logout also ends the current browser unlock. Password changes delete all that
user's reset/unlock rows. Navigation may discard local editing state; any
remaining authorization still expires after its fixed five-minute window.

Existing-user operations take the user row lock before locking/revalidating
its challenge. Username writes take ordered identifier locks first. This order
also governs credential invalidation so parallel reset/change operations do not
lock challenges in opposite order. SQL is parameterized; writable column names
are an internal field whitelist. Synchronous FastAPI handlers run database,
hashing and email calls outside the event loop.

## Postmark and HTTP boundary

Postmark remains the provider for verification, resend, reset, unlock and admin
signup notifications. Challenge changes commit before sending; no Postmark call
holds the database transaction open. Signup/unlock provider errors return a
recoverable 502 with their pending cookie retained. Signup opens Verify Email
with a warning and resend. Admin notification happens after user creation;
failure cannot undo a verified canonical account.

Unknown/disabled reset accounts receive the same generic acknowledgement and no
email. Reset provider failures also preserve that generic response and retain
any pending row so resend can recover without revealing eligibility. SQL/provider
error bodies, plaintext passwords, codes and opaque handles are not logged.

Lifecycle cookies are HttpOnly, SameSite Strict, Secure in production and scoped
to their relevant API paths. Handles are never placed in URLs. Reset needs only
its existing challenge cookie; no second reset-grant cookie is created. Origin
and `X-Requested-With: camOS` checks reuse the existing membership protection.
Responses including validation errors are no-store; validation input containing
credentials is not echoed. Account edits refresh shared authenticated identity.

## Simple automatic cleanup

Successful signup/reset rows are deleted in their completion transaction.
Verified unlock rows are deleted when editing ends, on logout/credential change,
or after expiry by cleanup. Consumed rows are inert and eligible for deletion.

Lifecycle requests and application startup attempt a best-effort batch of at
most 100 expired rows. Pending expiry derives from created_at plus one hour;
verified reset/unlock expiry derives from verified_at plus ten/five minutes.
Expired individual codes remain resendable until their pending journey deadline,
so cleanup does not prematurely remove those rows. `FOR UPDATE SKIP LOCKED`
prevents instances waiting on rows used by active requests. Local statement and
lock timeouts bound the deletion; failures produce a safe deferred-cleanup log
and do not fail the journey. Startup/request traffic drains abandoned rows over
bounded batches. There is no background worker, scheduler, cron, new service or
manual normal-operation row maintenance. No traffic and no startup means cleanup
waits until the next opportunity; expired rows never regain authorization.

Per-challenge bounds intentionally do not provide global login throttling or
prevent repeated abandonment and fresh challenge creation. No replacement global
limiter infrastructure is added.

## Migration and already-applied grants

`backend/migrations/002_canonical_user_lifecycle.sql` is administrator-only source
for future environments. It recognizes/configures BY DEFAULT identity, preserves
existing IDs, advances the existing sequence above the highest ID without moving
an already-ahead sequence backwards, recognizes the actual unique-index names,
adds only session_version to users, and creates exactly the 12-column challenge
table. It adds no other user metadata, tables or duplicate identifier indexes.
It does not add a created_at default. Runtime signup never computes a next ID.

The matching grant source records the already-applied privileges for
`portal-reader@camosbase.iam`: SELECT/INSERT/UPDATE on public.users, USAGE on
public.users_id_seq, and SELECT/INSERT/UPDATE/DELETE on challenges. No runtime DDL
or unrelated privileges are needed. These table-level user grants do not prohibit
status UPDATE at the SQL permission level; application models/field whitelists
prevent that product operation. Neither SQL file is run against production as
part of this correction. See backend/ENVIRONMENT.md for unchanged runtime secrets
and Postmark configuration.

## Scope and legacy boundaries

The polished My Account cards, validation, Save/Cancel, password controls,
loading/error/success states, mobile layout and accessible unlock dialog remain.
Only rejected contract/conflict behavior is removed, and Lock editing now ends
its database authorization. Organisation/membership/Manage Access, analytics,
Documents APIs/storage and other frozen product modules are unchanged. The shared
session tuple returns its original username; no document ownership compatibility
scheme remains in this auth phase.

Relevant JSON lifecycle routes/helpers remain retired from the prior change;
`/api/create-account` and `/api/password-reset/verify` return 410. Legacy JSON
Basic/password paths remain disabled by default and always disabled with
NODE_ENV=production. Explicit non-production compatibility, view-token mappings,
demo/contact/register-interest storage and local fixtures remain
outside this correction. View-token revocation is not claimed to follow canonical
session_version. No JSON user import or new legacy identity authority is added.

## Local verification and live acceptance

Tests use real disposable localhost PostgreSQL with the exact locked user and
challenge shapes, no created_at default, actual index names and actual runtime
grants. They verify identity allocation, concurrent completion, durable attempt
counters, opaque handles, automatic deletion, expiry and session revocation.
The Chromium suite drives the real test API and a local HTTP Postmark stub;
this proves provider integration locally, not delivery through live Postmark.
See canonical-user-lifecycle-delivery.md for exact commands/results/file manifest.

The owner will perform live-connected acceptance separately: existing canonical
login; new signup/Postmark verification; generated ID/created_at/version 0/zero
memberships; username/email login; reset with old password/session rejection;
My Account unlock, username/phone/password persistence; no completed signup/reset
rows; eventual abandoned-row cleanup; and unchanged organisation access flows.

Current historical API boundaries are exhaustively listed in
[compatibility-surface.md](compatibility-surface.md). They cannot create or validate
canonical customer/Admin sessions. Contact journaling remains unchanged.
