## Product and authentication

Visit `/admin` or `/admin/login` directly. There is no customer Admin navigation.
Only enabled canonical user ID **999999** authenticates. Username is read from
PostgreSQL, case-insensitively, and password verification uses canonical Argon2.
No production username/password is hardcoded. Raw Users hash editing never hashes
plaintext; increase `session_version` explicitly to revoke existing sessions.
Editing Admin status/version invalidates its session on the next request.

The separate HttpOnly `camos_admin_session` uses an eight-hour absolute lifetime,
production Secure, SameSite=Lax and path `/`. Signatures are domain-separated from
customer sessions and carry an explicit Admin purpose. Every Admin request reloads
the enabled canonical row and compares its version. Customer login and customer
session resolution reject ID999999. Customer reset initiation, resend, verification
and completion exclude it, including challenges issued before this change.
Admin logout clears only its cookie and remains available after expiry; customer
logout leaves the Admin cookie alone. No credentials/tokens persist in browser storage.

## APIs

- `POST /api/admin/login`, `GET /api/admin/me`, `POST /api/admin/logout`
- `GET /api/admin/tables`
- `GET /api/admin/tables/{table}/rows`: page_size default50/max100, fixed filters,
  deterministic primary-key keyset cursor; no mandatory COUNT.
- `GET /api/admin/tables/{table}/row`: complete primary-key query parameters.
- `POST /api/admin/tables/{table}/rows`: `{values: {...}}`, explicit INSERT.
- `PUT /api/admin/tables/{table}/row`: `{key: {...}, changes: {...}}`, explicit UPDATE.
- `GET /api/admin/organisations/{id}/context`: bounded sites and memberships with
  independent continuations, snapshot existence, gateway mapping and device counts.
- `POST /api/portal/organisations/{id}/disable`: customer active Owner only.

Every Admin response is no-store. Mutations require the existing origin/CSRF marker.
Errors do not expose SQL/provider credentials. Unknown tables/columns/body metadata
are rejected. No SQL, schema edit, generic DELETE or implicit upsert endpoint exists.

## Fixed row contract

The backend frozen registry contains exactly alarms, devices, gateways, memberships,
organisation_snapshots, organisations, site_snapshots, sites,
user_lifecycle_challenges and users. SQL identifiers originate only in this registry;
values are validated and bound as parameters. The browser consumes datatype metadata
but cannot change it. All persisted fields remain editable except stable primary keys.

- bigint: decimal strings, strict signed64-bit validation; user0 supported.
- integer/smallint: strict integers/ranges, booleans excluded.
- boolean: JSON true/false only.
- text: exact strings; empty does not mean NULL.
- UUID: validated/canonical UUID. Gateway creation requires operator UUID.
- timestamps: timezone-aware ISO, UTC transport retaining microseconds; no JS Date edit conversion.
- JSONB: parsed JSON bound explicitly as JSONB. Backend Decimal and frontend lossless
  JSON numbers preserve numeric precision. JSON `null` is JSONB null, not SQL NULL;
  all current JSONB fields are SQL NOT NULL. Duplicate JSON keys are rejected.
- bytea: reversible `\x` hexadecimal, never UTF8 decoding.
- SQL NULL: explicit nullable-field control; omission on create uses DB default/null;
  omission on update leaves the stored value alone.

Users/Organisations/Sites/Devices/Alarms IDs are generated by PostgreSQL and cannot
be supplied during create. All PKs remain immutable during update. Reserved999999
allocation fails and rolls back even if that row is absent; no automatic sequence
reseed. Snapshot keys, Gateway UUID and lifecycle text key are supplied at create.

PostgreSQL enforces unique/FK/check/not-null constraints; known enums, integer
bounds and positive intervals are validated early. SQLSTATE23505→409;
23503/23514/23502/22003→422; missing update→404. No automatic timestamp refresh
is added to raw row edits. Multi-user Admin raw updates have ordinary PostgreSQL
last-writer behaviour; no optimistic row version is invented.

## Snapshots and context

Context reports actual EXISTS/MISSING, independently of the customer Portal's
transient zero-snapshot fallback. Missing snapshots open Create; existing rows open
Update. Both payload and state are editable JSONB, including scalar/array/null JSON.
Dashboard-shape guidance is advisory; PostgreSQL-valid JSON is not prohibited.
A valid JSON object can still lack required Dashboard arrays/rollups and prevent
rendering. No automatic generation/template/history/synchronization is introduced.

Context is a repeatable-read, read-only transaction over the same canonical tables.
Sites/memberships are bounded at50(default)/100(max); devices use counts and links
into filtered paginated grids. Convenience actions open the same row editor.
Existing Portal catalogue/context/device/snapshot reads see committed changes on
its next relevant fetch. There is no duplicated store or sync service.

## Organisation soft deletion

Manage Access (`/settings/access`) shows Delete Organisation at its bottom only for
a loaded Owner response. Cancel-focused confirmation explains that data remains.
The backend independently rechecks enabled user, enabled organisation, active
membership and Owner role within a transaction using the existing organisation
advisory lock. It updates **only organisations.enabled=false**. No related rows or
explicit timestamps change. Admin membership/organisation writes share this lock.
The UI refreshes catalogue/pending access, clears obsolete selection and does not
refetch the deleted scope. Zero-org users remain authenticated. Internal Admin can
restore enabled=true without restoring or changing child rows.

## Focused follow-up: snapshot resolution and timestamp Now

Starting SHA: `9de2fdbf07a49df06d86e98c026426c2b9a68ddc`. This follow-up stays on `feat/internal-camos-admin` and contains exactly the two approved behavior changes.

Previously a persisted snapshot already took precedence over zero, but authenticated Dashboard reads could return incomplete object payloads or fail on non-object payloads. Both Organisation and Site authenticated Dashboard reads now use persisted data only when its envelope and payload are usable. Missing or unusable data selects the existing transient zero builder. Each request reads the canonical row, so a usable Admin-created or updated snapshot appears on the next request. Invalid rows, timestamps and state remain untouched; no persisted zero, repair, copying or synchronization is introduced. Demo/strict reads and the separate Reports reader retain their existing behavior.

The small read-time predicate follows the existing Dashboard projection/types and ReportsEngine domain checks: timezone-aware envelope timestamp; object payload; finite numeric rolling arrays of length 96; occupancy triples with minimum ≤ average ≤ maximum; 96 capacity pairs; named traffic entities with valid scope-specific IDs and matching 96 traffic-split widths; all seven period objects with numeric entrances/exits and occupancy triples; six age and two sex percentages totaling zero or 100. Additional JSON keys, capacity above 100, old timestamps and variable-length all-time buckets remain legal. No freshness rule or new validation framework was added. Admin writes still accept arbitrary syntactically valid JSONB, including `{}`, `[]`, `{"test":1}` and JSON `null`, without Dashboard shape validation.

Now uses an optional top-level `server_now` list of column names, separate from ordinary values, preserving arbitrary JSON objects and literal text. For example:

```json
{"values":{"organisation_id":"1","payload":{},"state":{}},"server_now":["ts","updated_at"]}
```

Updates use `{"key":...,"changes":...,"server_now":["updated_at"]}`. Omitting the list preserves the old API. Only editable, registered `timestamptz` fields may appear; unknown/immutable fields, duplicate names, other datatypes, malformed lists and simultaneous ordinary values for the same field are rejected. The typed pipeline obtains one `datetime.now(timezone.utc)` per mutation and binds the resulting real aware datetime through the existing parameterized SQL. No browser timestamp, string coercion or SQL-expression mechanism is involved. Frozen registry metadata and PK rules are unchanged.

RowEditor derives Now availability from each column's datatype. Selecting it hides manual entry and explains that server UTC time will be set on save; switching back restores the manual text. Manual timestamps retain microseconds, naive timestamps remain rejected, and existing SQL NULL, create default/omit and update unchanged modes are preserved. The snapshot editor note now describes the authenticated fallback behavior.
